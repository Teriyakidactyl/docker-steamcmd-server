# 🛠️ Author a SteamCMD Derivative Container

Use this procedure for a game or dedicated-server image that inherits from
`docker-steamcmd-server`. Keep generic SteamCMD, compatibility-layer,
supervision, and process-lifecycle behavior in the base; keep application
configuration, dependencies, persistence mappings, and application-specific
health behavior in the derivative.

## 1. Choose a supported base runtime

Select the least specialized supported base that satisfies the application.

Use a native tag such as `trixie` for a Linux server. Use a Wine tag such as
`trixie_wine-staging` for a Windows server. Use Proton only when the
application has been proved against a supported Proton row; Proton support is
not interchangeable with Wine and is currently amd64-only.

Prefer the stable supported alias when the derivative is intended to follow
validated base-runtime repairs. Pin a more specific base tag only when the
derivative deliberately owns that version boundary.

Do not copy SteamCMD, Wine, Proton, Box86/Box64, prefix initialization, or
generic process-supervision logic into the derivative.

## 2. Declare the application contract

Set the base application variables in the derivative Dockerfile and keep the
application command decomposed into executable plus arguments.

A minimal native declaration resembles:

```dockerfile
ARG BASE_IMAGE=ghcr.io/teriyakidactyl/docker-steamcmd-server
ARG BASE_TAG=trixie

FROM ${BASE_IMAGE}:${BASE_TAG}

ENV APP_NAME="example" \
    APP_EXE="example_server" \
    STEAM_SERVER_APPID="123456" \
    STEAM_PLATFORM_TYPE="linux"
```

For nested or unusual executables, set `APP_EXECUTABLE` explicitly. Prefer
`APP_ARGS_FILE` over shell-string `APP_ARGS` for new images. The base expands
argument files with `envsubst`, with one argument per non-comment line.

Install only derivative-specific packages in the derivative. A dependency does
not belong in the shared base merely because one game requires it.

## 3. Define and project the configuration API

Expose application settings through container environment variables when
operators need a stable Docker-facing API. Treat each exposed variable as an
ownership claim: on startup the container may reconcile that native setting
back to the API value, while native settings not exposed by the API remain
application/operator-owned.

### 3.1 Source every exposed setting

For every API variable, record the native setting, default provenance, and
source adjacent to the implementation. Prefer an authoritative upstream
settings/configuration URL.

Use comments that preserve the evidence a future maintainer would otherwise
have to rediscover:

```bash
# Upstream settings:
# https://vendor.example/docs/dedicated-server-settings
#
# Native setting: [Performance] ServerFPS
# Upstream default: 60
# Container API: SERVER_FPS
: "${SERVER_FPS:=60}"
```

Distinguish these default classes when they differ:

- **upstream default** — explicitly documented by the application vendor;
- **observed application default** — emitted by a named application/server
  build when authoritative documentation does not publish the exact value;
- **container default** — deliberately selected by the derivative.

When a key or default is only observed, identify the Steam AppID and the
application build/version used for the observation. Do not present an observed
or guessed value as an upstream default.

### 3.2 Validate and render desired settings

Validate ranges, booleans, enumerations, single-line constraints, quoting, and
application-specific escaping before rendering configuration.

`envsubst` is available in the base through `gettext-base`. Use it to render
a **desired-state fragment**, not the complete persisted native configuration.
Pass an explicit substitution allow-list so unrelated environment variables
cannot become accidental template inputs.

For example:

```bash
export GAME_CFG_NAME GAME_CFG_PORT

envsubst '${GAME_CFG_NAME} ${GAME_CFG_PORT}' \
  < /usr/local/share/example/container-owned.ini.in \
  > /tmp/container-owned.ini
```

`envsubst` performs substitution, not validation or escaping. Derive safe
internal substitution values from the public environment variables before
rendering.

### 3.3 Reconcile only container-owned keys

Merge the rendered desired-state fragment into the persistent native
configuration by section/key identity. If an owned key already has the desired
value, leave it unchanged. If it differs, update that key. Preserve unknown
sections and keys byte-for-byte where the chosen parser permits.

Do not regenerate the complete native configuration on every boot. Whole-file
rendering turns every future application setting into container-owned state and
can silently delete settings introduced by a game update or an operator.

Use this ownership rule:

```text
exposed container API key
    -> container-owned native setting

native setting with no container API entry
    -> application/operator-owned state
```

Write the persistent file only when reconciliation changes its content. This
provides semantic idempotence, avoids unnecessary filesystem churn, and
preserves forward compatibility with new native settings.

## 4. Establish persistence topology at runtime

Keep reconstructible installation/runtime state under `/app` and durable
game/configuration state under `/world`. The base reserves `/app/.steam` and
`/app/.compat`; derivatives must not repurpose those namespaces.

Create or repair application-specific links during a startup hook, not during
the image build. A volume mounted at `/app` or `/world` hides image-layer
files and symlinks beneath that mount.

Make persistence helpers converge both the link and its target. In particular,
do not return merely because an existing symlink already names the expected
target: the target may be absent on a newly created or restored volume.

A safe directory-link invariant is:

```text
source is expected symlink + target exists
    -> already converged

source is expected symlink + target missing
    -> create target, then continue

source is real directory
    -> create target, migrate contents, replace source with symlink

source is unexpected symlink
    -> fail or repair deliberately; never silently preserve ambiguous topology
```

Preserve `/world` as potentially irreplaceable state. Treat `/app` as
reconstructible but expensive; retaining it avoids unnecessary depot and
compatibility-runtime reconstruction.

## 5. Validate first start and recreation

Test the same lifecycle an operator will exercise.

For a fresh first start, prove that:

- SteamCMD installs or updates the selected AppID successfully;
- the selected compatibility layer initializes to its completion marker when
  applicable;
- derivative prerequisites complete;
- runtime persistence links resolve to existing writable targets;
- the real application executable starts; and
- the health check reaches its ready condition.

Then recreate the container with the same `/app` and `/world` volumes and
prove that:

- application manifests and depot data are reused;
- compatibility prefixes and derivative completion markers are reused;
- persistence topology repairs idempotently;
- configuration reconciliation makes no change when inputs are unchanged; and
- the application reaches readiness again.

A same-container restart does not prove recreation persistence. Use separate
container instances sharing the same named volumes when automating this test.

## 6. Document the operator contract

Document every public environment variable in the derivative root README. For
application settings, include at least:

| Field | Required content |
| --- | --- |
| Environment variable | Stable container-facing API name |
| Container default | Value used when the variable is unset |
| Native setting | File/section/key or equivalent application location |
| Meaning | Operator-visible effect |
| Source | Authoritative settings documentation, or explicit observed-build provenance |

Link the derivative README to the authoritative upstream settings/configuration
documentation used to construct the API. Keep irreversible or destructive
native settings explicit; do not enable them merely because they exist.

Explain which settings the container owns and state that unknown/native-only
settings remain preserved. An operator should be able to predict whether a
manual native-config edit will survive the next startup.

## 7. Check the derivative boundary

Before publication, confirm that the derivative contains only
application-specific behavior.

Move a capability into `docker-steamcmd-server` only when it is generic across
derivatives and its lifecycle belongs to the shared runtime. Keep application
packages, native settings, save/config paths, compatibility prerequisites, and
application-aware health behavior in the derivative.

Add comments for non-obvious failure modes and version boundaries. Explain why
the implementation exists, what previously failed, and what a future change
must re-prove rather than merely narrating the current line of code.
